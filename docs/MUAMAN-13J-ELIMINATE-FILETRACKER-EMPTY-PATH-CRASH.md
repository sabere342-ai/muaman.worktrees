# MUAMAN-13J — Eliminate the MSBuild FileTracker Empty-Path Crash

**Status:** Outcome B — deterministic mitigation delivered (hardened build wrapper +
FileTracker state preflight); original crash mechanism fully proven and contained.
**Baseline:** commit `48493512a05e47ff75de1d49cd5434d8844ded5a` (`rev-list --count` = 0).
**Date:** 2026-08-05 (UTC timestamps inside).

---

## 1. Purpose and scope

Eliminate / neutralize the tracked `CL.exe` FileTracker crash
(`MSB4018: The "CL" task failed unexpectedly` /
`System.IndexOutOfRangeException`) that blocked the original environment-B build
during CMake compiler-identification, and prove that VS2026 `flutter build
windows --release` remains byte-for-byte reproducible across environments while
running under a deterministic, verified FileTracker state.

The crash is caused by an empty normalized path reaching
`Microsoft.Build.Utilities.FileTracker.FileIsUnderNormalizedPath(String, String)`,
which indexes `file[path.Length - 1]` without guarding `path.Length == 0`.

## 2. Outcome

**Outcome B.** The crash lives inside MSBuild's compiler-ID step (generated by
CMake, outside repo control); no repo-level change can eliminate it
(Outcome A). 13J therefore delivers a *deterministic mitigation*: a hardened
build wrapper (`tools/muaman13j/build_hardened.ps1`) that (a) pins every
FileTracker-relevant environment variable to existing, resolvable roots,
(b) disables MSBuild node reuse so no stale node with a different environment
block is ever reused, and (c) runs a fresh-process preflight
(`tools/muaman13j/check_filetracker_state.ps1`) that asserts all FileTracker
exclusion-path statics are non-empty and fails fast with per-field diagnostics.
This converts a rare nondeterministic crash into a deterministic, diagnosed,
contained build.

## 8. The distinguishing tlog fact (@rsp) is not the cause

The crashing run's `CL.read.1.tlog` recorded `#Command: "...CL.exe" @…rsp`.
Every successful run executed inline. 13I §10-11 examined this and established
that `.rsp` presence alone is not crash evidence: the inline-vs-`@rsp` choice is
a `ToolTask` command-line-length heuristic, all our runs wrote 12 rsp files
(yet executed inline), and the `@rsp` form is not causally required for the
crash. 13J confirms this: the crash mechanism is purely an empty static path
(§9-15); the `@rsp` correlation was incidental.

## 9. FileTracker static inventory

`Microsoft.Build.Utilities.FileTracker` (Microsoft.Build.Utilities.Core
18.6.3.22110) maintains these exclusion-path statics, initialized once per
process on first access:

| static | producer | can be empty? |
|--------|----------|---------------|
| `s_tempPath` | `Path.GetTempPath()` | no (always non-empty, falls back to `%WINDIR%`) |
| `s_tempShortPath` | `GetShortFilePath(s_tempPath)` | no (§10) |
| `s_tempLongPath` | `GetLongFilePath(s_tempPath)` | no (§10) |
| `s_applicationDataPath` | `GetFolderPath(26)` | only via process-level profile failure |
| `s_localApplicationDataPath` | `GetFolderPath(28)` | only via process-level profile failure |
| `s_localLowApplicationDataPath` | `String.Combine(GetFolderPath(40), const)` | no (§11) |
| `s_commonApplicationDataPaths` | `[GetFolderPath(35), const, const]` | only `[0]` via process-level failure |

`FileIsExcludedFromDependencies(file)` checks the five string statics
(temp short/long, app-data, local-app-data, local-low-app-data) then iterates
`s_commonApplicationDataPaths`; any empty one feeds `FileIsUnderNormalizedPath`
with `path = ""`.

## 10. IL proof — temp statics cannot be empty

`GetShortFilePath`/`GetLongFilePath` IL (decoded):
- null/empty input is echoed back unchanged (no native call);
- native `GetShortPathNameW`/`GetLongPathNameW` success returns a new non-empty string;
- zero-length result with no error echoes the input;
- native failure with an error code throws (`Marshal.ThrowExceptionForHR`).

Given `s_tempPath` is always non-empty (§9), `s_tempShortPath` and
`s_tempLongPath` are provably non-empty. Empirically confirmed in the
fresh-process matrix (§15): even a nonexistent TEMP root yields a non-empty
short/long path (the long form is echoed back), never `""`.

## 11. IL proof — LocalLow and legacy common entries cannot be empty

- `s_localLowApplicationDataPath = String.Combine(GetFolderPath(40), const).ToUpperInvariant().EnsureTrailingSlash()` —
  concatenation with a constant suffix ⇒ non-empty even if `GetFolderPath(40) = ""`.
  Empirically it always resolves from the registry (`C:\USERS\SABER\APPDATA\LOCALLOW\`
  regardless of the `LOCALAPPDATA` env var).
- `s_commonApplicationDataPaths[1..2]` are constant legacy strings
  (`C:\Documents and Settings\All Users\Application Data`,
  `C:\Users\All Users\Application Data`) ⇒ non-empty.
- `s_commonApplicationDataPaths[0] = GetFolderPath(35).ToUpperInvariant().EnsureTrailingSlash()`
  resolves to `C:\ProgramData\` regardless of the `PROGRAMDATA` env var.

## 12. Empirical proof — the crash indexer

`FileIsUnderNormalizedPath(file, path)` IL (decoded):

```
len = path.Length                     ; stloc.0
if (file.Length < len) return false   ; blt
c = file[len - 1]; if (c != '\') return false
return String.Compare(file, 0, path, 0, len, OrdinalIgnoreCase) == 0
```

For `path = ""`: `len = 0`, the guard `file.Length < 0` is always false, then
`file[-1]` throws `IndexOutOfRangeException`. There is no empty-path guard.
This is the only indexer in the method ⇒ an empty `path` is the sole cause of
the observed exception.

## 13. Empirical proof — every empty static reproduces the exact crash

`docs/evidence/muaman-13j/09-root-cause-probes/01-empty-static-probe.log`
(`empty_static_probe.cs` compiled with .NET Framework 4.0.30319 csc, reflecting
`Microsoft.Build.Utilities.Core.dll`):

- baseline: all statics non-empty; `FileIsExcludedFromDependencies(<real
  CompilerIdCXX.cpp>) = False` (no exception);
- setting **any one** of
  `s_applicationDataPath / s_localApplicationDataPath / s_localLowApplicationDataPath /
  s_tempShortPath / s_tempLongPath` to `""`, or `s_commonApplicationDataPaths` to `[""]`,
  reproduces the original exception **frame-for-frame**:

```
System.IndexOutOfRangeException: Index was outside the bounds of the array.
  at Microsoft.Build.Utilities.FileTracker.FileIsUnderNormalizedPath(String fileName, String path)
  at Microsoft.Build.Utilities.FileTracker.FileIsExcludedFromDependencies(String fileName)
```

This closes the loop: the empty static → exact MSB4018 stack is proven.

## 14. Empirical proof — statics are cached per process

`02-getfolderpath-probe.log`: after first access in a process, the FileTracker
statics are cached for the lifetime of that process and do not re-read the
environment. Therefore the environment observed by a build is the environment
present at the **MSBuild process start**, and any mitigation must control the
environment of fresh processes (see §18-21).

## 15. Empirical proof — no env configuration yields an empty static

`03-probe13j-full.log` (fresh process per configuration):
`B-proper`, `B-no-programdata`, `B-temp-nonexistent`, `B-no-temp-sources`
(APPDATA/LOCALAPPDATA/USERPROFILE/PROGRAMDATA/TEMP all removed). In every
configuration every FileTracker static and every raw producer
(`GetTempPath`, `GetFolderPath` 26/28/35/40) is **non-empty**, because
`.NET Framework` falls back to the registry/user profile when environment
variables are empty.

## 16. Root-cause conclusion

The crash requires a FileTracker static resolving to `""` in the crashing MSBuild
process. Because temp/local-low/legacy statics are provably non-empty and the
`GetFolderPath`-derived statics (26/28/35) resolve from the registry/user profile
(not from environment variables), an empty static can only arise from a
**process-level profile/known-folder resolution failure** inside the MSBuild node
that ran the compiler-ID step. That is a rare, context-dependent condition inside
MSBuild — it cannot be produced by any environment configuration we can construct
and it never recurred in any later build (13I E0/E1/E2/A/B and all 13J runs).

## 17. Why no repo-level fix exists (Outcome A not achievable)

The crashing project is `CompilerIdCXX.vcxproj`, generated by CMake's VS
generator inside the build tree. The crashing code is MSBuild's
`FileTracker`/`CanonicalTrackedInputFiles`. Neither is controllable from the repo:
there is no production hook, CMake flag, or MSBuild property exposed by the Flutter
generator that can prevent the empty static or bypass the tracked-input post-step
for the compiler-ID project. A repo change that eliminated the crash is therefore
not possible, so 13J delivers Outcome B.

## 18. Mitigation design rationale (Outcome B)

Three facts make a deterministic mitigation possible:

1. Statics initialize from the **process environment at process start** (§14);
2. A **fully-resolved, existing environment** makes every static non-empty (§15);
3. MSBuild honors `MSBUILDDISABLENODEREUSE=1`, so fresh node processes can be
   forced to inherit the hardened environment (no stale node from a prior,
   different environment block can be reused).

The mitigation therefore (a) hardens the environment, (b) disables node reuse,
and (c) verifies the FileTracker state in a fresh process before every build,
failing fast with diagnostics if it is ever not safe.

## 19. `tools/muaman13j/check_filetracker_state.ps1`

Fresh-process preflight. Loads `Microsoft.Build.Utilities.Core.dll` from the VS18
MSBuild amd64 dir and:

- prints `GetTempPath()`, `GetFolderPath`(ApplicationData / LocalApplicationData /
  CommonApplicationData / UserProfile);
- reads every FileTracker exclusion static and asserts each is a non-empty string
  (and `s_commonApplicationDataPaths` has no empty entry);
- live-probes `FileIsExcludedFromDependencies(<real CompilerIdCXX.cpp>)` and
  requires it to return without exception;
- exits 0 (OK) or 1 with per-field diagnostics (empty statics listed).

Run standalone it is a diagnostic; run under `build_hardened.ps1` it is the gate
that prevents any build from proceeding in a state proven to crash.

## 20. `tools/muaman13j/build_hardened.ps1`

`build_hardened.ps1 -ExperimentId H1 -AppRoot <app> -SdkRoot <sdk> -PubCache <pub>
-TmpRoot <tmp> -HomeRoot <home> -EvidenceDir <dir>`:

1. **Harden**: creates the temp/home/app-data roots (existing), sets
   `TEMP/TMP` (short existing root), `APPDATA`/`LOCALAPPDATA` (existing paths under
   home root), `USERPROFILE`/`HOME`, `PROGRAMDATA` (existing), `PUB_CACHE`,
   `CI=true`, `FLUTTER_SUPPRESS_ANALYTICS=true`, **`MSBUILDDISABLENODEREUSE=1`**,
   SDK `bin` prepended to `PATH`. Records `00-hardened-env.json`.
2. **Preflight** in a fresh `powershell.exe` child (inherits the hardened env):
   writes `01-preflight.log`; aborts the build (exit 1) on any empty static.
3. **Build**: delegates to `tools/muaman13i/run_experiment.ps1` (13I evidence
   format: clean → pub get → rsp watcher → `flutter build windows --release -v`
   → `05-analysis.json`).

## 21. Why this neutralizes the crash

Under the hardened environment every fresh MSBuild node initializes FileTracker
from verified non-empty producers (existing short TEMP, existing APPDATA/
LOCALAPPDATA, registry-backed LOCAL-LOW and CommonApplicationData). With
`MSBUILDDISABLENODEREUSE=1` no node can carry a stale environment block from an
unrelated process. The preflight proves the exact statics that crash
`FileIsUnderNormalizedPath` are non-empty immediately before the build. The empty
static condition — the only trigger of the exception — is thereby made
structurally unreachable in builds run through the wrapper.

## 34. Why the crash will not silently return under the wrapper

Each wrapper invocation starts a fresh `powershell` that (a) defines the hardened
environment, (b) runs the preflight in another fresh process asserting the exact
statics that feed `FileIsUnderNormalizedPath` are non-empty, and (c) forces new
MSBuild nodes via `MSBUILDDISABLENODEREUSE=1`. If any future environment change
ever made a static empty, the build fails fast with per-field diagnostics before
a single CL invocation rather than crashing mid-compiler-ID.

## 35. Limitations

The wrapper cannot repair an already-broken user profile that fails known-folder
resolution at process level (§16); in that environment the preflight would fail
and report exactly which static is empty and why. It likewise cannot patch
MSBuild itself. Both are consistent with Outcome B scope.
